## Failure recovery and learning strategy

When implementation, infrastructure or training fails repeatedly, change the investigation or approach instead of repeating the same commands, reviews or training run. Apply this workflow at the first recurrence of the same unexplained failure, or when a completed experiment misses its stated quality target:

1. **Locate the failure.** Inspect the actual error, relevant logs and last successful checkpoint. Distinguish transport/runtime/resource failures from input/label problems, objective/model limitations and integration defects. A disconnected stream is not evidence that the learning strategy failed; a completed training run is not evidence that the model works. Use the smallest reproduction needed to distinguish plausible causes.
2. **Read previous attempts first.** Consult the existing task handoff and experiment ledger before retrying, researching or assigning another worker. Reuse retained inputs, results and working components. Repeat a failed attempt only with a stated changed condition or hypothesis; a bounded retry for an evidenced transient failure is reasonable. Do not relaunch unchanged runs, duplicate another owner's investigation or reopen completed reviews.
3. **Research analogous failures and working approaches.** Search the web using the concrete error, component/version and task symptoms. Look for relevant issue threads, documentation, papers, public implementations, model cards and successful training recipes. Check whether their assumptions, data, hardware and versions match ours. Record useful links, versions and the reason an approach applies; reuse prior research rather than repeating discovery. Public development research is already authorized within the boundaries below.
4. **Choose a materially different, justified next step.** Address the diagnosed cause: repair data or labels, improve hard negatives and abstention examples, change representation/loss, reuse a suitable pretrained model or harness, or revise the architecture. For ML, consider supervised classification or ranking for evidence selection/linking, regression for genuinely continuous targets, distillation for transferring supported teacher behavior, and preference learning or reinforcement learning when reliable preferences or a verifiable reward and suitable feedback loop exist. RL is not a default cure for poor labels, missing evidence or infrastructure faults. Teacher outputs remain provisional unless independently qualified.
5. **Run one bounded comparison.** State the hypothesis, smallest useful change, baseline, task-relevant success criteria and stop condition before execution. Change one principal factor where practical and record coupled changes. Preserve source-family splits and label provenance; use training/development data for iteration, keep teachers blind to protected evaluation, and never tune on or reopen a closed held-out set. A changed objective or output contract needs a comparable baseline. Judge source support, correct building/floor association and unsupported claims where relevant, not training loss alone. Preserve the single learner/GPU owner and measured hardware limits.
6. **Leave compact, reusable evidence.** Update the existing task or ML ledger with the failure signature, attempted approach, relevant code/model/data/configuration references, result, conclusion and next decision. Link retained logs or receipts rather than generating expanding reports. Mark rejected approaches and the condition that would justify revisiting them. Include this history in ownership handoffs so a fresh worker does not restart a failed loop.
7. **Return to delivery.** Implement the supported fix or alternative, perform only the relevant lean checks, integrate usable results and move on. Continue independent authorized work while a lane is blocked. If progress requires missing data, access or an external change, report that specific prerequisite and preserve the checkpoint instead of consuming time on repeated tests, retries or speculative training. Do not weaken source integrity, access controls or quality criteria to make a run appear successful.

**Conditional language distillation:** follow [the distillation procedure](docs/orchestration/delivery-reset-20261004/ML_DATA_PLAN.md#conditional-language-distillation) and task D08D.

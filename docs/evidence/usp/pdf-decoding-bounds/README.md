# PDF-BOUND-01 — native PDF decode containment

Base: `85eaaa3a60533d8588e21424fa2da92b7b2da625`. The parser is pinned to `pypdf==5.5.0` in `services/geo/requirements.txt`; the checked local image was `sha256:338a4e73941c4baae72def6637cf695be22df7246afbf73828c0ee875333e812`. Its `PageObject.get_contents()` constructs `ContentStream` and eagerly decodes/joins content streams before the old 8 MiB check. `PdfReader` also decodes object/xref streams while resolving pages; text extraction can decode font maps and form content. A page-only precheck therefore cannot cover the native-text route.

`geo.native_pdf` now runs the entire pypdf parse in a fresh child. Before reading source bytes or importing pypdf, it installs a 384 MiB hard address-space limit on Linux or a 384 MiB Windows Job Object process-memory limit. A 45-second parent timeout kills the child. Input remains limited to 10 MiB; the existing 100-page, 8 MiB decoded-page and 250,000-character checks and page/line/paragraph locators remain. The child returns only bounded page text or an explicit input/resource/filter error. There is no in-process fallback or parser-global setting. The original remains outside Git and unchanged.

The 8 MiB page check still occurs after decode, but that decode is confined to a hard-capped process; a hostile PDF may consume up to the 384 MiB ceiling and return a resource error. Unsupported pypdf filters return an explicit error. This does not establish universal PDF safety, OCR, source interpretation accuracy, API-stack runtime, ownership, or any release gate.

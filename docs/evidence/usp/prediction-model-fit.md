## What the application must predict

The [adaptive ingestion plan](../../orchestration/ADAPTIVE_INGESTION_EXECUTION.md) separates field/operation suggestions from later evidence-backed document-to-building/floor links. [Learning evidence](../../api/learning.md) shows the current E5 field mapper and a retained Qwen3-Reranker-0.6B text-pair checkpoint. Qwen's single local development pass on 25 fields found 7/7 positives and four false mappings on 18 negatives at an uncalibrated threshold; lexical had three false mappings. V6/V7 E5 candidates failed useful calibration, and held-out evaluation remains unopened. No model has demonstrated correct document association, floor identity, Indian-language scan interpretation or forecasting here.

Prediction here is mostly **closed-set judgment** over records already retrieved: choose a known field meaning; flag relevance or contradiction; rank a cited passage against candidate buildings, then candidate floors only under a supported parent; or abstain when the source has no match. It is not a time-series forecast. Unknown, absent, conflicting and no-match must have distinct outputs. Exact identifiers, arithmetic, source integrity, parent constraints, permissions, citations and publication remain deterministic code/record decisions. A well-formed typed answer or a high model score cannot create a missing property fact.

The TypeSafe API is a vendor-hosted service, not an open-weight Jev release. Its SDK/interface alone would not enable local inference. Similarly, JSON schema validity in an OpenAI response is not a calibrated class probability or proof that a cited pixel/region supports the answer. Vision interpretation should follow an immutable page/region crop and retain its source hash, crop geometry and result version; use OCR/layout as the first measurable path for text-bearing scans.

A shared `/v1/systemone` shape, typed result or vendor/community benchmark does not establish equivalent semantics, field accuracy or calibrated no-match decisions. Code licences and weight licences are separate. Model-card revisions were observed on 30 September; no weights were obtained in this task. **Adjacent task-specific models.** Retained [Qwen3-Reranker-0.6B](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B/tree/e61197ed45024b0ed8a2d74b80b4d909f1255473) remains the better-shaped path for cited passage → parent-constrained candidate ranking: [our local receipt](../../api/learning.md#open-model-fit-review--desktop-29-september-2026) measured ~1.22 GB peak allocated GPU memory for a development pass, but no link or no-match accuracy. [GLiNER2.5 multilingual boundary model](https://huggingface.co/fastino/gliner2.5-multi-v1/tree/2ca71aafb3446d9014e1c55c7ff51c9bc7209c47) (Apache-2.0, 287M; [code](https://github.com/fastino-ai/GLiNER2/tree/55656fbfa01d3d4a77485e1a1eeeaf682990ccdf)) is more relevant than a generic classifier when the need is **source text spans, entities and candidate relations**: its card specifies half-open offsets into original text. It still cannot attach a span to a real original page or canonical building by itself; preserve the extractor's source/page/region locators. The older [GLiNER2 base](https://huggingface.co/fastino/gliner2-base-v1/tree/f9634218e53580c56edf0de97ca1a7d3f1c2354e) is English and a different span architecture; do not transfer 2.5 multilingual claims to it. [Multilingual mDeBERTa NLI](https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-mnli-xnli/tree/8adb042d524ecd5c26d3e3ba0e3fbcf7e2d0864c) remains a direct entailment/contradiction comparator, but its card explicitly warns that FP16 is unsupported. GLiClass/SetFit are generic classifier tools; they do not replace these task-shaped models merely by emitting scores.

The reviewed decision interfaces above consume text; no image-decision path was established for them. This does not assert that every underlying base architecture is text-only. [PaddleOCR-VL-1.6 and Qwen3.5-2B](../../api/learning.md#open-model-fit-review--desktop-29-september-2026) are separately identified extraction/visual-interpretation candidates with no local qualification; the current document owner is already trialing bounded CPU OCR. An OCR transcript or vision answer is an observation to verify against the original, not a relationship label.

## Smallest useful next decision

Keep deterministic mapping/rules and the frozen Qwen learner experiment as the current path. After that result returns, **one offline Von model-only shadow pass** on already reviewed V8 development/calibration field profiles would test the most direct small typed alternative. Pin model, code and prompt; disable chains, refuse truncated inputs, include explicit no-match, and report wrong mappings, positive coverage, abstentions, score reliability, runtime and peak RAM/VRAM against lexical/Qwen receipts. Do not fit or select a threshold on untouched families, and do not present Von's publisher calibration as ours. If labels are too sparse for no-match/reliability, record that gap rather than force a decision. For later cited relationships, retain the Qwen parent-constrained ranking route and evaluate GLiNER2.5 only when real cited span/relation labels exist. For images, first require an actual source-backed scan question and region-level expected answer; neither the unverified “Decisions API” name nor fluent visual output supplies that evidence.

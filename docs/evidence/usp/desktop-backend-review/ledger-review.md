## Findings

1. **P2 — The parcel relationship is used without authorizing its evidence source, and the identifier loses its locator.** `packages/server/src/modules/officer/building-ledger.ts:55-65,87-94` derives the parcel assertion from a confirmed `occupies_parcel` edge, but cites only root, registry-record and identifier sources. It never cites `association.evidence` or the parcel feature's source, and the identifier query omits `external_identifiers.evidence.locator`; line 90 substitutes the generic text `validated official_ulpin assertion`. Trigger: a current edge cited by a parcel source whose case is now archived, while the root and identifier sources remain available. The ledger can still expose the edge and ULPIN, without the edge source passing `registrySourceTx`; the same omission applies to `detailed_record`/`shared_space` seed edges in `relatedRegistryRecords`. The exact identifier locator is also absent from the response. The existing consolidated register cites both association and parcel source evidence before its source-authority loop (`consolidated-register.ts:126,169,177`), and the identifier writer stores the exact locator (`area-resolver.ts:267-277`). Expected: authorize every source that supports a projected relationship and return its actual retained locator, or leave the relationship unavailable. This is a static path trace, not an executed revocation test.

2. **P2 — The `LIMIT 201` sentinels silently truncate parcel and identifier assertions.** `building-ledger.ts:55-65` reads at most 201 confirmed parcel rows, filters stale revisions only afterward, then reads at most 201 identifiers; neither query checks overflow or sets `HasMore`. More than 201 matching rows, including stale links sorted before a current one, can hide a current parcel; more than 201 validated identifiers can hide a second value that would make a parcel conflict. Lines 97-112 then present the truncated set as the complete `parcelUlpin` state. Expected: apply current-revision pins before the parcel cap and reject or explicitly mark either overflow, as the history arrays do at lines 119-121. Actual: no overflow state or error. Static SQL/control-flow finding; no large corpus was built.

3. **P2 — Partial current parcel coverage is reported as `recorded` with no missing notice.** `building-ledger.ts:25-34,97-112` computes state only from returned identifiers and adds the missing message only when there are zero assertions. With two current confirmed parcels and one validated official ULPIN, it returns `recorded`, one assertion and no indication that the second parcel lacks an anchor. H26 distinguishes reviewed partial from complete anchors; the response exposes neither the full current parcel set nor a partial state. Expected: keep the missing parcel explicit without inventing an identifier. This also occurs below both query limits. Static branch trace; positive multi-parcel runtime was not available in the retained NYC source.

4. **P3 — The ledger's record cap now changes the existing dossier route.** `packages/server/src/modules/officer/officer.ts:282-297,354` replaces the dossier's prior unbounded graph query with `relatedRegistryRecords`, which throws `422 BUILDING_LEDGER_LIMIT` at 2,001 current linked records. `GET /api/v1/buildings/{buildingId}/dossier` previously returned those records; it now fails even though only the new ledger needed this cap. Preserve the old consumer's documented behavior or coordinate an explicit paged/limited dossier contract. This is a code-diff compatibility finding; no 2,001-record source was constructed.

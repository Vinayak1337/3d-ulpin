## Retire or replace source behavior, while preserving history

- **Synthetic-only dataset intake is not official intake.** `features/spatial/reference-import/adapter.ts:11-35`, `source-normalizer.ts:5-17` and `source-adapters.ts:14,30,104-117` require synthetic classification and can generate fictional `DEMO-3D` assertions. `lib/server/spatial-datasets.ts:28-58` stores the original bytes with integrity checks, but writes a fictional description and synthetic classification; `spatial-dataset-db.ts:7-23` constrains the table to that class. Keep existing records/originals and any required read compatibility. Replace the active intake with a provenance-backed profile; never relabel existing unknown/synthetic data as official. `reference-import/{package,browser,survey-assets}.ts` contain reusable bounded ZIP/hash/raster logic mixed with that legacy flow, so split and qualify it rather than copying it wholesale.
- **Demo and prototype paths need exact decisions.** `lib/server/area-scenario.ts:26-85` builds an invented crossing behind `area-routes.ts:168`; `domain.ts:910-945` and the catch-all route's `demo-files`/`demo-assets` branches expose fixtures; `features/spatial/data/calibration.ts:4-11,35-71` and `data/publications.ts:4-16` create a public synthetic GLB route; `features/studio/data/district.ts` and `features/studio/types.ts:1-13` contain the authored Lake View neighbourhood and invented occupancy. Isolate historical tests and saved URLs first, then retire these operational routes/values explicitly. `registry-seed.ts:24-90` is a real import service, but `:225-235,269-275,313-363` contains a demo-only Nandan rights/association branch that must be split. Do not drop the whole importer.
- **Presentation cannot create source facts.** `features/spatial/compiler/architecture.ts:64-121` constructs schematic windows, balconies, roof props and storey treatment from a footprint/height; road markings are gated to synthetic at `:39-55`, while roof props are not. Preserve bounded GLB compilation and record-to-feature identity, but remove or constrain inferred architectural details for official scenes under H30. The frontend-owned `reference-runtime/{architecture,environment}.js` is likewise a renderer for the legacy authored scene, not a source of property facts. `features/spatial/data/core-display.ts:64-83` labels its elevation offsets and ground plane as display-only, yet `:85-87` infers Google/OSM attribution from names. - **Local access and legacy defaults are not deployment identity.** `lib/server/usp/principal.ts:7-26` enforces loopback but supplies `local-demo-operator`; `lib/server/db.ts:127-133` defaults the event actor to that string. `registry-db.ts:6-7` and `registry-routes.ts:62-66` default sites synthetic, which is a historical workflow choice, not a fact to assign to new operational data. Existing `queued/running/stale` job states and observed/planned/hypothetical/synthetic source classifications are valid software statuses when backed by records; their presence does not invent an issuer, right, coordinate frame or height. `source-catalog.ts`/`area-acquisitions.ts:14-20,75-98,145-174` implement a bounded NYC test source and fixture path, not a general Indian official-source acquisition gateway.

# Backend API route inventory and cleanup plan

**Scope:** API route surface and backend dispatch only. This document records the current checkout as inspected on 2026-09-26. It is an inventory and sequencing plan; it does not authorize backend edits, route removals, or UI changes.

## Current route map

Unless written in full, paths below are relative to `/api/v1`. Brace groups abbreviate separate endpoints; this is a family inventory, not the final method-by-method contract map.

The public app API is under `apps/web/app/api`. The root `/api` handler in `app/api/route.ts` reports service/version information and the health path. Most legacy workbench requests enter `app/api/v1/[...path]/route.ts`, which applies the local-request guard and dispatches to workspace capabilities, officer, officer AI, area, and registry routers before handling health, source files, and cases. The catchall exports GET, POST, and PATCH; unhandled combinations become 404s. `lib/server/errors.ts` and route-local handlers shape errors, but response envelopes and request IDs are not uniform across all route families.

## Cleanup sequence

1. **Freeze a route/consumer contract map.** For each method and path, record the request schema, response/error envelope, local-request/auth guard, size limits, idempotency or revision behavior, storage/database side effects and all callers. Include direct route files as well as catchall branches. Mark compatibility URLs and downloads explicitly.
2. **Reduce catchall ownership without changing URLs.** Keep the catchall as a thin adapter while moving only clearly bounded legacy case/source operations into a named router module. Officer, area and registry modules are already separated; do not combine them merely for file-count reduction. Retain HTTP methods, status codes, headers and request/response shapes until consumers are migrated deliberately.
3. **Align shared HTTP contracts.** Compare the generic catchall, dataset handlers, spatial-ML route, core reads and USP handler. Specify consistent error codes, request IDs, cache/security headers and method behavior where appropriate. Keep distinct domain errors and USP envelopes where clients rely on them. Check validation at runtime at each boundary; TypeScript types alone do not validate request bytes.
4. **Review duplicate spatial entry points by capability.** Map dataset-level ML against the shared spatial-ML service and identify shared job/artifact contracts. Consolidate implementation only when source identity, hashes, calibration, bounded payload behavior and artifact authorization remain equivalent. Do not collapse distinct inspection/import formats or the core legacy-read bridge into model inference.
5. **Close the route retirement loop.** Search route declarations, generated links, client helpers, tests/fixtures and docs for each retired path. Remove dead references only after confirming no saved URL or retained workflow relies on it. Record any compatibility redirect/404 decision and update the route contract map.
6. **Verify proportionally before any implementation handoff.** Use the operating guide’s risk-based checks: route-level behavior and client contract checks for changed paths; preserve source-integrity, stale-event, partial-publication, privacy and semantic-error checks where affected. Report actual command/exits and distinguish code checks from official-source accuracy, qualification and deployment. This plan itself has not run tests or proposed a runtime gate pass.

## Guardrails for any later route work

- No route removal based only on naming, apparent duplication, a mockup, or lack of a current visible link. Confirm server actions and URL construction first.
- Keep originals, hashes, issuer/original URL, acquisition metadata and provenance attached through import, registry, spatial and packet paths. Do not replace source records or seed a new snapshot as cleanup.
- Preserve unknown, absent, null, withheld and conflicting states; geometry or scene display does not establish ownership or issuance.
- Maintain local-only protection unless a separately authorized deployment/security design changes it. Do not introduce provider calls as part of route cleanup.
- Backend changes may update contracts and client wiring when required for compatibility. UI redesign and UI implementation remain outside this backend plan.

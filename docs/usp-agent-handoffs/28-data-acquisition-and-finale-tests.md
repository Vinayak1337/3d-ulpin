# 28 — Dataset acquisition and finale test plan

**Owner: DATA; contracts: FND; independent review: lead-appointed reviewer. Aligned 24 September 2026.** This restores the acquisition runbook previously in H00, preserving D0–D7 meanings. Catalogue research is not acquisition or runtime qualification. Use [release-plan.json](release-plan.json) for gate status; all new finale tests below are **planned**, not executed.

## 1. Start with a matched bundle, then separate benchmarks

For GF0, select one permitted Indian building/site with a plan, section/level schedule and a reliable site/building association. Prefer a multi-unit example with a basement/shared space, but do not invent those features if unavailable. Add parcel/controls/utility evidence only when it really covers the same area, reference and date. An unrelated public plan plus an unrelated point cloud does not form a matched bundle.

In parallel, retain D0 authored cases for exact algorithmic truth, D1 for real roof-shape regression, and independent D6 modality benchmarks. Start with one inspected sample per modality, then a bounded 100–1,000-object corpus where applicable. An initial 20–50 independently reviewed AI examples per selected task is a feasibility cohort, not a defensible general accuracy claim. Freeze site/source-family holdouts before tuning; report sample counts, label uncertainty and uncovered classes.

If a matched real internal building remains unavailable, software tests may continue with clearly authored D0 cases and separate real exterior/modality samples. **The end-to-end real-Indian interior/rights claim stays unqualified.** The demo and PPT must state that gap; assembling unrelated sources cannot pass it. No Delhi-only prerequisite.

### Runtime receipt contract

When executed, each runtime group writes `receipt.json` under `docs/evidence/usp/finale/<test-id>/` (full-product groups under `docs/evidence/usp/full-product/<test-id>/`). Use `schemaVersion: ulpin-test-receipt/1`, exact `testId`, `status: passed|failed|blocked`, full `codeCommit`, `manifestHash`, nonempty `sourceHashes`, `modelHashes` (empty only for deterministic cases), UTC `runAt`, nonempty `environment`, actual `command`, integer `exitCode`, nonempty `expectedActual` cases and `artifacts` with relative path and SHA-256. Each case records `caseId`, independent `expected`, observed `actual`, and `result`; a passing receipt has exit 0 and all cases passed. Keep sanitized local artifacts or sanitized hashes/results; private files never enter Git.

A gate may be marked complete only with complete prerequisites, passed named tests and gate evidence containing those exact per-test receipts. Historical baseline docs cannot satisfy a new test merely by existing. The plan validator checks paths, IDs, metadata and artifact hashes, not the truth of execution or whether an oracle was independent; reviewer acceptance is still required. A plan-validation receipt cannot pass any runtime gate.

D0 aliases remain `B-A`, `B-B`, `P-A`, `P-B`, `U-A101`, `U-A102`, `STAIR-S1`, `DUPLEX-D1`; resolve actual IDs from import receipts, never copied DB UUIDs. Independent numerical oracles include 10×10 squares with 1 m X overlap and 2 m Z overlap: **10 m² / 20 m³**; Z-boundary-only contact: **0 positive volume**; 10×10 outer minus 2×2 hole: **96 m²**. For these exact synthetic arithmetic cases use 1e-6 absolute tolerance, not as a claim of survey accuracy. Keep invalid conflict drafts separate from the clean record. Include `ONLY_A101`, `NEVER_A102`, `SHARED_STAIR_CONTEXT` in distinct synthetic page regions for scope leakage checks.

## 7. Full-product campaigns and reporting

FP-LEARN retains H21 parameter-update, untouched family holdout, eligible labels, immutable models, shadow/promotion/pending-only handover/rollback and contention tests. FP-PUBLIC retains H13 contributor isolation, quarantine/scanner outage, review, status, revocation and notification tests; shared identity lookup never exposes personal submissions. FP-ENRICH tests that generated facts cannot affect measurements/readiness/rights/evidence exports. FP-ASSIST tests grounding, prompt injection, typed tools and bounded access. FP-FORMATS qualifies each reader separately; a supported-layout success is not new-format support.

FP-SCALE uses real unique-building cohorts at 10k → 100k → 1M, separately measuring backend ingestion and spatially paged display. Do not clone data, raise parser/scene limits or keep an entire corpus resident. Native tile extraction needs its own tested bounded reader and exact lineage. Retain original geometry/LoD/part/source identities and same-area context; correlated upstream datasets are not independent truth. Stop at the highest actually passed rung. FP-DEPLOY separately qualifies Indian hosting, egress, credentials, access controls, restore, retention and backups before activation.

For every claim report requested/admitted/accepted/rejected/unresolved/renderable/analytically-eligible counts; measured conversion and total latency; first persisted selectable scene; worker RSS/CPU/storage/network; frame/selection p50/p95; domain accuracy with denominator/holdout; and human correction effort. Fix device, version, warm/cold state and workload first. No metric is invented to make the PPT appear completed. H24 specifies how to present measured results, targets and unavailable evidence.

## A. Outcome and release boundary

GF2 demonstrates source-linked candidates for the SIH domain tasks: building extraction, plan/floor segmentation, vertical delineation and explainable topology. It also qualifies one RERA carpet-area comparison where sources support it; GF3 qualifies the sanctioned-versus-observed comparison using the same candidate/geometry contracts. GF0 data/contracts and GF1 identity/exchange precede GF2; GF3 consumes its reviewed quantities/findings through RIGHTS and the existing IMPACT0 path; GF4 makes the exact-revision PACK card; GF5 records actual results and rehearsal. The root release plan is the gate/status authority.

The `full_product` lane retains the concurrent adaptive learner, public dashboard, MCP, enrichment and large-scale qualification. They are product commitments, not prerequisites for GF2. GF2 can use deterministic methods and bounded, versioned models. No AI candidate allocates a 3D identifier, changes source coordinates, becomes a canonical measured solid or records a right without the existing review command. Synthetic adverse cases are labelled fixtures. Missing matched permitted data leaves the corresponding real-source claim unqualified while the supported D0 flow remains available.

### GF-AI exit boundary and baseline choices

Finale GF-AI requires **two genuinely learned inference routes**: a building-mask extractor and a plan-segmentation model, each with licensed pinned weights, model hash, preprocessing/class-map version and untouched independently labelled evaluation. A trained external checkpoint may be reused only where its licence and labels fit; otherwise train/fine-tune on permitted labels and record the training lineage. Do not require training from scratch or during the live demo. If suitable weights/data/evaluation are missing, the ML gate remains open; deterministic vector parsing/roofer alone cannot pass it or be advertised as learned extraction.

Initial building-model candidate: a compact [Torchvision DeepLabV3](https://docs.pytorch.org/vision/stable/models/deeplabv3.html) segmentation baseline, with a building-specific output head and permitted building labels. Generic pretrained class sets are not presumed to include a qualified aerial-building target. Initial raster-plan candidate: the [CubiCasa5K reference floor-plan model](https://github.com/CubiCasa/CubiCasa5k), after separately checking code/weights/dataset licences and class coverage, with targeted adaptation only if allowed and independently beneficial. These are implementation candidates, not installed or validated models. Pin compatible dependencies; use vector/CAD evidence directly where available rather than rasterizing away precision merely to invoke ML.

Vertical delineation combines reviewed learned/vector boundaries with supplied level evidence through deterministic geometry. Topology uses explainable deterministic checks; learned anomaly ranking is optional until labelled data justifies it. Report those methods separately, never claim four trained models. Freeze quantitative acceptance thresholds and minimum per-class/site coverage against a declared task and baseline in GF0, before holdout evaluation; a small feasibility cohort alone cannot support general reliability claims. Unknown/failed class coverage cannot be hidden in a pooled score.

## B. Common candidate and review contract

Every task returns `DomainCandidate {task, taskVersion, sourceParts, inputManifest, sourcePermission, frameAndHeightPins, methodNameAndVersion, modelHash?, parameterHash, outputKind, outputRef?, confidenceOrError?, coverage, limitations, state, reviewAction}`. `modelHash` is required for learned routes and absent only for explicitly deterministic methods. `state` is `candidate | abstained | unsupported | failed | reviewed`; none means recorded. The output ref points to an immutable derivative, not overwritten original bytes. A reviewer can accept a mapped fact/draft through INGEST's existing checked command, reject it with a reason, or request a missing source. Store candidate → reviewer → accepted geometry/source revision lineage. Rerunning a model creates a new candidate/version; a changed source, transform or label policy makes the old one stale.

For each task DATA freezes the source licence/permission, independently annotated truth, split by building or source family, tolerance, minimum useful coverage and negative examples **before** evaluation. A model's own predictions cannot be its oracle. Record input/output hashes, method/runtime version, observed precision/recall or measurement error, abstention/unsupported rates, per-source coverage and actual processing time. A retained result shown on stage is identified as preprocessed with its measured runtime; only lightweight selection, comparison and review steps are called live. A backup recording is labelled separately.

## C. Qualified 3D geometry and topology

The first numerical profile remains FIND's tested planar/prism/slab operation. [PostGIS 3.5's SFCGAL reference](https://postgis.net/docs/manual-3.5/en/reference_sfcgal.html) names the optional CG operations, subject to the runtime checks below. Optional true closed-solid analysis requires FND to probe the running `postgis_full_version()` and `pg_extension` for the enabled SFCGAL extension and pin the operation versions. The repository's PostgreSQL 17/PostGIS 3.5 dependency does not prove SFCGAL is enabled or a particular input type is valid. Qualify accepted representation and orientation/closedness before each operation; `CG_MakeSolid` does not validate an invalid shell, and `CG_Volume` may return zero for a surface representation. Probe `CG_3DIntersection`, `CG_3DDifference`, `CG_3DUnion` and volume only with supported valid types. Run val3dity as a complementary solid-validity test for its supported profile. It cannot decide which physical/legal spaces may overlap.

FIND's response carries `operationProfile, representationType, validity, sourcePins, framePins, coverage, state, contact, intersectionComponents, areaM2|null, volumeM3|null, reasonCode`. An open/invalid/unsupported solid, missing SFCGAL, incompatible datum or failed operation gives `not_assessed` and `volumeM3:null`, **never a zero-conflict finding**. Numeric zero is permitted only for a qualified valid assessed pair. The fixture includes an open shell that superficially returns zero, a closed overlapping pair with independently calculated volume, boundary contact, a valid void and a disconnected/duplex component. Save the SQL/function, extension/version, val3dity result and expected/actual output.

Geometric validity and cadastral/domain rules are separate. Parent building/unit containment is legitimate context; two incompatible exclusive unit assertions can overlap by positive volume even if one is wholly contained in the other. A shared-use assertion does not imply an exclusive conflict. Complete partition coverage can be tested only against a source-supported complete envelope and component inventory; atria, structural voids, setbacks and technical/common space may be valid. Different floor outlines are not inherently anomalies. Residuals and stack outliers become explainable review findings with source/coverage, not automatic illegality. Learned ranking may prioritize review but cannot suppress a critical deterministic finding. RIGHTS supplies reviewed interest/validity context separately and FIND never adjudicates title.

## D. Carpet-area and sanctioned/observed checks

`CarpetComponent` records an exact unit/source revision, plan locator, polygon or measured area, one mutually exclusive class (`net_usable`, `internal_partition`, `external_wall`, `service_shaft`, `exclusive_balcony_or_verandah`, `exclusive_open_terrace`, `other_or_unknown`), scale/units, reviewer and inclusion rule version. The [RERA section 2(k) quantity](https://www.indiacode.nic.in/indiacode/bitstream/123456789/2158/1/A201616.pdf) includes net usable area and internal partition walls; it excludes external walls, service shafts, exclusive balcony/verandah and exclusive open terrace. The component ledger defines the starting polygon and prevents double counting/subtraction. If an external wall, shaft or terrace cannot be separated from a generic unit footprint, report `not_assessed` for the statutory quantity. A room sum or raw footprint is not a substitute.

`CarpetCheck` pins source-supported computed amount, declared comparison amount, both quantity definitions, component manifest, independent hand-calculation oracle, frozen rounding/tolerance, coverage and finding state. A mismatched definition or revision yields `not_comparable`; missing component class yields `not_assessed`; a beyond-tolerance difference yields a review finding, not a legal violation. **GF-T17** uses a known external wall, internal partition, shaft, exclusive balcony/verandah and open terrace plus one ambiguous component. DATA hand-calculates the expected area independently and freezes tolerance before the run. Test wrong area definition, stale source and a matching negative case; report actual error/coverage.

`DeviationPair` pins separately sourced sanctioned and observed assets, building/phase/level matching, both dates/revisions, geometry and height type, horizontal/vertical frames, qualified transform/control residuals, coverage and comparison tolerance. A planned drawing is not observed construction; an estimated storey count is not a measured height. Use independent registration/control checks rather than forcing best fit to erase a possible deviation. Preserve source height values and benchmark; convert ellipsoidal, orthometric or local levels only through a qualified operation. Compare height, count and footprint/extent only where both sources support the same quantity and region; report uncertainty bands and unassessed areas. A discrepancy is a review finding, not an automatic unlawful-construction verdict.

**GF-T19** pairs matched sanctioned and observed revisions with independent control points, a legitimate revised plan, measurement noise, a seeded extra-level case and a seeded setback case. DATA supplies expected counts/height/extent and negative-case oracles; DOMAIN records actual errors, alignment residual, tolerance and abstentions. Missing or incompatible datum/phase, insufficient control, changed sanctioned revision or source-only imagery must yield `not_comparable`/`not_assessed`, never a fabricated extra floor. GF-T18 geometry/relationship cases are owned by FIND in H12; GF-T20 reuses IMPACT0 in [17](17-infrastructure-impact-screening.md).

5. UI demonstrates one coherent selected building/source/identity/revision, candidate-to-review transition and explicit uncertainty. GF5 records actual output hashes, errors, processing time, live versus retained steps and failure fallback.

Tests must prove source hash unchanged; candidate and accepted draft use separate revisions; stale worker/review cannot publish; unsupported/missing data remains unknown; no AI output allocates an ID, source height or legal result.

The manifest's reason for excluding `doitt_id` incorrectly calls its wire value numeric. Audit the existing field labels and distinguish issuer-declared types from observed wire types before another training run. This is an **experimental, unpromoted** field/operation candidate. It scores only the three existing building mappings: `building.sourceKey` with `literal_identifier@1`, `building.name` with `literal_text@1`, and `building.geometry` with `geojson_polygon@1`. It does not read arbitrary documents, normalize raster or point-cloud payloads, infer ownership, convert geometry, or change ingestion routing. The deterministic registry and validation remain the authority.

## Evidence and eligibility

The corrected checked corpus is [`learning-corpus.json`](learning-corpus.json), version `usp-field-mapping-corpus-v2`. It records source URL, issuer, geography, acquisition date, unchanged sample and issuer-metadata byte hashes, permission basis, field definitions, evidence links, label decisions, issuer-declared types, observed wire shapes, and source-family split. New originals and the model stay outside Git in `/Users/vinayak/.codex/task-data/ai-06a-learning/`. NOLA and NYC are training families; San Francisco is excluded from training and threshold choice but was already observed during the earlier run, so the corrected comparison is **diagnostic, not a fresh generalization test**. The acquired NYC sample excludes the retained `DOITT_ID=353927` benchmark feature. All three foreign families are research-only and excluded from Indian production training qualification.

The New Orleans portal calls its source building footprints and declares a public-domain licence. Its sampled `globalid` is text; a 28 September 2026 issuer API count returned 162,486 rows and 162,486 non-null distinct values. NYC's issuer dictionary calls `DOITT_ID` a consistent unique key and declares its column numeric. All five values in the unchanged research GeoJSON sample are JSON strings, as are all 1,662 values in the separately retained NYC 10013 original; the latter are distinct within that subset. The existing exact string-copy operation can use the sampled wire values, so `properties.doitt_id` is now a positive `building.sourceKey` schema label. NYC `name` retains a positive building-name meaning even though all five sample keys are **present with null values**: those rows cannot execute a name copy. NYC BIN remains unknown because the issuer documents duplicate/placeholder values, while parcel keys remain unknown because their linkage role lies outside this corpus's target vocabulary. San Francisco's issuer dictionary identifies `sf16_bldgid` as a building ID, `p2010_name` as a building name when present, and `shape` as MultiPolygon; two of five sampled names are null. NOLA `GEOPIN`, `StructureID`, and `OBJECTID`; NYC `OBJECTID`; and SF alternate IDs remain unknown for documented semantic/stability gaps, despite string wire values. No Sarvam output, teacher agreement, private tenant content, or generated example enters the corpus.

The learner builds field profiles from paths, issuer definitions, declared types, and aggregate wire shapes, null and absent counts. It never embeds raw IDs, name values, coordinates, or complete source rows. The loader recomputes each recorded wire observation from the unchanged original and rejects contradictions. The decoder uses observed string wire values for the string-copy/text targets, even when the issuer declares a numeric column; a declared text field with all null sample values remains a semantic candidate with zero wire-compatible rows. GeoJSON polygon geometry is a separate wire case. These checks are shallow: they do not establish uniqueness for an arbitrary new row, CRS/topology validity, or whole-row conversion eligibility. Checked field/target decisions are deduplicated at the source-layout level; five building rows from one issuer still contribute one schema example per field. Original hashes are checked before training and inference.

The labels and scores concern **semantic field matching**, not permission to execute a conversion on every row. For example, NYC's name column has the building-name meaning even though the acquired names are null. The existing `literal_text@1` admission still rejects an incomplete name mapping, and geometry still needs independent validation. Keep semantic matches, executable-operation eligibility and actual conversion correctness separate in any future collector or runtime integration; this corpus does not qualify the latter two.

The base is the MIT-licensed [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small) revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`, loaded locally with `trust_remote_code=False`. Its `model.safetensors` SHA-256 is `1a55775f53449dac10a2bcbc312469fac40b96d53198c407081a831f81c98477`. Full required-file hashes are in the run receipt. Its last BERT encoder layer alone was fine-tuned on CPU with 24 AdamW steps, seed 17, two Torch threads, and a maximum of 128 input tokens. The source and target texts use E5's `query:` and `passage:` prefixes with mean pooling. The threshold for each encoder was selected only on its training-family scores.

## Measured result

| Route | SF diagnostic exact fields | Correct positive mappings | Positive abstentions | False maps on negative fields |
| --- | ---: | ---: | ---: | ---: |
| Generic lexical/type rule | 6/6 | 3/3 | 0/3 | 0/3 |
| Unchanged E5 | 4/6 | 1/3 | 2/3 | 0/3 |
| Fine-tuned E5 | 5/6 | 2/3 | 1/3 | 0/3 |

There were **11 checked training fields** (5 positive), **6 SF diagnostic fields** (3 positive), and **10 explicitly unknown fields** excluded from training/evaluation. NYC tax-lot and SF parcel keys are unknown because their linkage role is outside this three-target building vocabulary, rather than blanket negatives. Base E5 made 8/11 exact training decisions; tuned E5 made 9/11 but falsely mapped NOLA `activestatus` to `building.sourceKey` and mapped NYC's null-only `name` to the wrong target. On SF the tuned model mapped the building ID and geometry but abstained on the name. Peak process RSS was 1,218,412,544 bytes and elapsed run time was 7.045 seconds on the local M3. This result does not beat the inexpensive lexical/type rule or qualify a general learner. The candidate remains offline; no production model, provider route, queue worker, or API contract was changed.
